### 1. 私聊撤回后消息回弹（用户主诉）
**根因**：`private_messages` 表有 `recalled` 列，撤回时后端也确实 `UPDATE ... SET recalled = 1`，但两处私聊历史查询的 SELECT 漏选 `recalled` 字段，重新加载历史时撤回标记被丢弃 → 前端 `ChatBubble.vue:27` 的 `message.recalled === 1` 不成立，原始内容重新渲染。
- `apps/chat/backend/routes.js:401`、`:407`（REST 私聊历史，含分页）
- `server/src/ws/chat-server.js:266` `stmtGetPrivateHistory`
- 对照：公共聊天室（routes.js:49/53）与群聊（:297/303）都带了 `recalled`，**只有私聊两处漏了** → 解释"特别是私聊"。

### 2. 实时消息需不断刷新（用户补充主诉）★ 最重要
**根因**：`server/src/utils/relay-handlers.js:158` 的 `isRelayDuplicate()` 里写了
```js
.all.apply(null, values);   // ✗ this = null
```
better-sqlite3 的 statement 方法内部依赖 `this` 访问原生句柄，`this=null` 抛
`TypeError: Illegal invocation` → 该函数被 `private_message`/`new_message`/`group_message` 共用，**导致中继消息（来自 peer 服务器/AstrBot 侧）的入库与推送整条链路失败**。表现为：对方（跨服务器/机器人）发来的消息不会实时到达，只有本地历史接口能拉到 → "要不断刷新页面"。
- 服务端错误日志可见高频 `[RelayBus] private_message error: Illegal invocation`（13:58–14:29 密集出现）。
- 修复：改为 `var stmt = ctx.db.prepare(...); var recent = stmt.all.apply(stmt, values);`
- 验证：修复后离线复现脚本不再报错，且真实写入数据库；重启后错误日志中 `Illegal invocation` 完全消失。

### 3. poll 长轮询游标竞态（潜在丢消息）
`client/src/utils/websocket.js` 旧逻辑用 `server_time`（响应返回时刻）当下一轮 `since`，而事件 `ts` 是入队时刻。若事件在「服务端取完 events 之后、响应返回之前」入队，其 `ts < server_time`，下一轮 `since` 会永久跳过它。已通过复现脚本证实丢失。
- 修复：引入全局单调递增事件序号 `seq`（`chat-server.js` 的 `pollSeqCounter`），poll 接口接受 `since_seq` 并回传 `last_seq`，客户端以序号为主游标、时间戳仅作旧版兜底。
- 注意 `seq` 从 1 开始，**首次 poll 的 `sinceSeq=0` 必须走序号分支**，故判定用 `Number.isFinite` 而非 `> 0`。
- 复现脚本结论：旧逻辑丢事件，新逻辑正常收到。

### 4. 重连补偿（体验加固）

## 聊天使用体验专项（同日第二轮，用户指令「重点注意聊天的使用体验」）

### 5. realtime.js 永不重连 + 401 空转（遗留项修复）
`client/src/utils/realtime.js`：`catch` 里 `self.stopped = true; self.connect();` 与 `connect()` 开头 `if (!self.stopped) return` 自相矛盾，该路径永不重连。
- 改为 catch 中保持 `stopped=false` 并退避重连（5s）；`_poll` 增加 401 短路（置 stopped 停止轮询，交登录流程重新 connect）与指数退避 `_retryDelay`（100ms→10s 封顶）。
- `disconnect()` 重置 `inFlight` 与 `_retryDelay`。

### 6. 发送状态不可靠（核心体验缺陷）★
**问题**：`wsManager.send()` 无返回值，三个发送 action 调用后立即 commit 并 resolve，`getMessageStatus` 默认返回 `'sent'`。结果：WS 未连接时消息入离线队列、队列满（50）后**静默丢弃**，但 UI 显示"已发送"∎对勾。
**修复链**：
- `websocket.js` `send()` 返回 `'sent' | 'queued' | 'dropped'`（WS 异常降级入队返回 queued，队列满返回 dropped）。
- `chat.js` 三个 action（sendMessage / sendPrivateMessage / sendGroupMessage）`return result || 'sent'` 透传。
- `Chat.vue` 新增 `_applySendResult(tempId, result)` 统一落状态：dropped → `failed` + toast；queued → `sending`；sent → `sent`。`sendMessage` 与转发路径（`sendForwardTo`，原为裸 `wsManager.send`）均改用该辅助方法。
- `getMessageStatus` 支持 tempId 状态键，未记录状态但仍是临时消息时回退 `'sending'`。

### 7. poll 模式异步发送结果回传
`_sendViaHttp` 是 fire-and-forget，`send()` 已返回 `'sent'`，其 catch 分支原为静默丢弃。
- 改为经事件总线回传：能入队则 `emit('send_queued', {temp_id})`，队列满则 `emit('send_failed', {temp_id})`。
- `Chat.vue` 注册对应 handler：`send_failed` → 置 failed + toast；`send_queued` → 置 sending。

### 8. `_flushOfflineQueue` 潜在死循环
原 `while (queue.length) { send(shift) }`——若 send 因通道未就绪又把消息 push 回队尾，会无限空转。改为按返回值判定：返回 `'queued'` 即 break，等下次连接事件再冲刷。

### 9. tempId 未清理导致状态永远「发送中」
`UPDATE_MESSAGE_ID`（公共）与 `UPDATE_GROUP_MESSAGE_ID`（群聊）只改 `id` 却**没有删 `tempId`**（私聊的 `REPLACE_TEMP_MESSAGE` 有 `Vue.delete`）。若保留 tempId，`getMessageStatus` 会命中旧状态键，已确认的消息永远显示转圈。

## 公共聊天室点击不滚到底部（同日第四轮，用户报障）

### 18. `selectChat` 的公共分支是空实现 ★
**现象**：点击侧栏「公共聊天室」，消息列表停在中间或顶部，不显示最新消息。
**根因（两层）**：
1. `Chat.vue` 的 `selectChat(chatId)` 中，`if (chatId === 'public') { // nothing extra }` —— **只有公共分支没有 `scrollToBottom()`**；私聊分支（`loadPrivateMessages().then` → 滚底）与群聊分支（`loadGroupMessages().then` → 滚底）都有。公共房间消息来自全局 `store.messages`，无需重新拉取，但"不需要拉取"被错误地等同于"不需要定位"。
2. 消息容器是同一个 `div.chat-messages`（`ref="messageContainer"`），**没有 `:key="currentChat"` 强制重建**，只有 `v-if / v-else-if` 空状态分支。切会话时 DOM 原地复用 → 浏览器保留上一个会话的 `scrollTop` → 表现为停在中间/顶部。
**修复**：公共分支补两级 `$nextTick` 的 `scrollToBottom()`——第一级等 Vue 渲染出切换后的消息列表，第二级等 `transition-group` 完成布局后再定 `scrollTop`，避免被渲染竞态覆盖。
**注意**：`scrollToBottom()` 内部本身已含一次 `$nextTick`，故实际是"三级等待"，对 `transition-group` 的消息列表是必要的。
**教训**：多分支 if/else 里，任何一个分支缺少其他分支共有的收尾动作（这里是"定位视口"）都会形成隐蔽的体验缺口；`// nothing extra` 这类空注释是危险信号，应显式说明"为什么可以不做"。
